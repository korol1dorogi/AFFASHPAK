# Безопасность

Документ задач L8 и OPS2: что проверено и как защищено. Сквозные правила — [AGENTS.md](../AGENTS.md), раздел «Безопасность». Сводный чек-лист — [в конце](#итоговый-чек-лист-ops2-22102026).

## Загрузка документов (проверено 21.10.2026)

Клиент загружает выписки, договоры и отчётность (`POST /api/applications/{id}/documents`), сотрудник банка их скачивает. Опасность двойная: файл может навредить серверу, если тот его исполнит или разберёт уязвимой библиотекой, и тому, кто его откроет, — PDF-просмотрщик сотрудника выполняет встроенный JavaScript, запускает вложения и автодействия.

### Сервер файл не исполняет
- В бэкенде нет библиотек, которые разбирают PDF или изображения (ни PDF-парсеров, ни Pillow, ни ImageMagick): файл сервером не открывается, не рендерится и не конвертируется.
- Файл хранится под случайным именем `documents/<uuid>.<расширение по типу>` (`apps/documents/storage.py`); имя клиента — только для показа, в путь не попадает (`names.py`).
- Права на файл — `0640`, на каталог — `0750` (`FILE_UPLOAD_PERMISSIONS`): без бита исполнения, другим пользователям системы не читается.
- Каталог `media` не отдаётся веб-сервером: в Caddy нет маршрута на него, файл можно получить только через API после проверки доступа.
- Отдача — всегда вложение (`Content-Disposition: attachment`), `X-Content-Type-Options: nosniff`, тип — тот, что определён по содержимому, не присланный клиентом; на всём сайте CSP `default-src 'self'` (`deploy/caddy/Caddyfile`). Браузер файл не исполняет и не показывает как HTML.

### Что проверяется при загрузке
По порядку, отказ — ответ 400 с понятным текстом, файл не сохраняется (`apps/documents/services.py`):
1. Доступ: заявка своей компании (чужая — 404), статус, в котором загрузка разрешена (иначе 409).
2. Размер: не пустой и не больше `UPLOAD_MAX_FILE_BYTES` (10 МБ; больше — 413).
3. Тип — по первым байтам, а не по имени и заголовку клиента: только PDF, PNG, JPEG (`signatures.py`).
4. Содержимое — `apps/documents/inspection.py`, только стандартная библиотека Python:
   - **во всех файлах** нет HTML, `<script>`, `<svg>`, `<iframe>`, `<?php`, `javascript:` — так ловятся «полиглоты»: картинка или PDF, которые браузер мог бы прочитать как страницу;
   - **PDF:** корректный заголовок `%PDF-1.0…2.0`; файл кончается на `%%EOF`, после него — только пробелы (иначе к PDF дописан другой файл); нет активного содержимого — `/JavaScript`, `/JS`, `/Launch`, `/EmbeddedFile(s)`, `/RichMedia`, `/XFA`, `/SubmitForm`, `/ImportData`, `/GoToE`, `/AA`; имена проверяются после раскрытия экранирования (`/J#61vaScript` = `/JavaScript`) и внутри сжатых потоков (FlateDecode распаковывается с лимитом 64 МБ на файл — защита от «zip-бомбы»); зашифрованный PDF отклоняется: его содержимое не проверить. `/OpenAction` сам по себе разрешён — им LibreOffice и сканеры открывают первую страницу; опасное, что он мог бы запустить, отклоняется по списку выше;
   - **PNG:** цепочка чанков с проверкой CRC, первый — `IHDR`, после `IEND` ничего нет;
   - **JPEG:** файл кончается маркером `FFD9` — ничего не дописано.
5. Отказ пишется в лог (`upload rejected: application, user, тип, причина`) — без содержимого файла.

Тесты: `apps/documents/tests/test_inspection.py` (JavaScript в действиях и в сжатом потоке, обфусцированные имена, Launch, вложения, XFA, автодействия, шифрование, HTML и программа после `%%EOF`, «zip-бомба», PHP и ZIP после картинки, битые PNG и JPEG), `test_security.py` (через API: вредоносный файл → 400, в базе и на диске ничего), `test_signatures.py`. Демо-PDF (`data/sample/documents`) и PDF коллекции Postman проверку проходят.

### Чего нет и почему
- **Антивирус (ClamAV и т. п.)** — отдельный сервис и зависимость; для синтетических демо-данных не нужен. На проде с реальными клиентами — обязателен, вместе с санитизацией PDF (пересборка без активного содержимого) перед показом сотруднику.
- **Проверка изображений декодером** — нужна библиотека (Pillow); структурной проверки и отказа от всего, что дописано после конца файла, для прототипа достаточно.

## SQL-инъекции (проверено 21.10.2026)

- **Сырого SQL нет:** все запросы — через Django ORM, значения уходят в базу параметрами. Ни `raw()`, ни `extra()`, ни `RawSQL`, ни `cursor.execute()` в коде нет; ruff с правилами bandit (`S608`, `S610`, `S611`) роняет CI, если они появятся.
- **Динамика только из белых списков:** сортировка и фильтры очереди банка (`ordering`, `status`, `product_kind`, `grade`, `assignee`) — `ChoiceField`/`RegexField`, другое значение — 400. Поиск по ИНН и названию — `startswith`/`icontains` с параметром. id в путях — конвертер `int`. ИНН в реестре — `^\d{10}(\d{2})?$`.
- **Проверено атакой на живой стек:** 8 типовых payload'ов (`' OR '1'='1`, `UNION SELECT … FROM auth_user`, `; DROP TABLE …`, `pg_sleep`) в ~22 параметра — логин, регистрацию, демо-вход, поиск и фильтры очереди, реестр, id заявок и продуктов, подбор, создание заявки, сотрудников. Итог: обхода входа нет, поиск возвращает 0 записей, таблицы целы, `pg_sleep` не выполнился, 500 нет. Входные данные возвращаются только как текст ошибки валидации в JSON.
- Тесты: `apps/core/tests/test_injection.py`.

## XSS (проверено 21.10.2026)

- **Бэкенд HTML не отдаёт:** только JSON; `mark_safe`, `format_html`, `|safe` и шаблонов в API нет (ruff `S308`). Данные хранятся как ввели — экранирует тот, кто показывает.
- **Фронт выводит данные только как текст:** React экранирует всё в JSX; `dangerouslySetInnerHTML`, `innerHTML`, `eval` не используются — biome (`noDangerouslySetInnerHtml`) роняет CI. Ссылки строятся из путей приложения и id; `download_url` формирует сервер.
- **Редирект после входа** (`?next=`) — только путь этого сайта: `//…`, `/\…`, `javascript:` и управляющие символы отклоняются (`safeNext`).
- **Скачивание:** имя файла без `< > : " / \ | ? *`, `Content-Disposition: attachment`, `nosniff` — даже файл с HTML внутри браузер не откроет как страницу.
- **Вторая линия на стенде:** CSP `script-src 'self'` без `unsafe-inline` (Caddy) — встроенные и чужие скрипты не выполнятся, даже если экранирование где-то пропустит; в собранном `index.html` inline-скриптов нет.
- **Проверено атакой:** payload'ы `<img onerror>`, `<svg onload>`, `<script>`, `javascript:` записаны во все поля, которые пишут клиент и банк (имя, название компании, цель, залог, должность, имя файла, ответ на запрос, запрос данных, комментарий, причины отказа и советы), и открыты на всех экранах клиента и банка. Ни один не выполнился, в DOM ничего не внедрено, клиент видит их как текст.
- Тесты: `frontend/src/app/security.test.tsx`, `apps/core/tests/test_injection.py`.

## Лимит тела запроса (проверено 22.10.2026)

- **Caddy** обрезает тело больше 11 МиБ ответом 413 ещё до gunicorn (`request_body { max_size 11MiB }` в `deploy/caddy/Caddyfile`). Самое большое законное тело — один документ: 10 МиБ (`UPLOAD_MAX_FILE_BYTES`) плюс обвязка multipart.
- **Django** — вторая линия: `DATA_UPLOAD_MAX_MEMORY_SIZE` = 10 МиБ + 64 КиБ, документ больше 10 МиБ — 413 (`apps/documents`). JSON-поля ограничены сериализаторами (`maxLength` в контракте: цель 1000, сообщение ассистенту 2000 символов).
- Проверено через Caddy локально (`docker compose up web`): тело 12 МБ с верным CSRF-токеном → 413, обычный вход → ответ Django.

## Сотрудники компании (проверено 22.10.2026)

- **Только с согласия.** Подписант не добавляет сотрудника, а приглашает по логину; `Membership` создаётся, когда адресат сам принял приглашение (`POST /api/invitations/{id}/accept`). Раньше `POST /api/company/members` по одному логину добавлял любого свободного клиента в чужую компанию, в том числе подписантом, и тот уже не мог подключить свою (D23).
- **Без перебора логинов.** Приглашение отвечает 201 на любой логин правильного формата — нет такого, работает в другой компании или это сотрудник банка, ответ один. 409 только про свою компанию: логин уже в ней или уже приглашён.
- **Чужое приглашение → 404**, отозванное или отклонённое принять нельзя; одновременные «принять» сериализуются блокировкой пользователя, двух компаний не будет. Тесты — раздел «invitations» в `apps/business/tests/test_company.py`.
- **Остаётся:** регистрация отвечает «Этот логин уже занят» — это перечисление логинов анонимно, как почти в любом сервисе с логинами; для кабинета без email и телефона риск принят.

## Лимиты запросов (проверено 22.10.2026)

- **Общий счётчик.** Счётчики троттлинга живут в кэше Django. LocMemCache держит свой счётчик в каждом процессе, и на стенде с тремя воркерами gunicorn вместо 10 входов в минуту проходило 30. Теперь кэш — таблица в PostgreSQL (`DatabaseCache`, `settings.CACHES`), её создаёт миграция `apps/core/migrations/0001_cache_table.py`, поэтому достаточно обычного `migrate`. Redis появится в стеке с OPS4 — тогда кэш можно перенести туда.
- **IP клиента.** `NUM_PROXIES = 1` (`DRF_NUM_PROXIES`): идентификатор — последний адрес в `X-Forwarded-For`, тот, что добавил Caddy; всё, что клиент дописал перед ним, игнорируется (`test_a_spoofed_forwarded_for_does_not_reset_the_limit`). Caddy сам отбрасывает присланный клиентом заголовок, а порт backend на стенде не опубликован — напрямую в gunicorn не попасть.

## Аудит зависимостей (проверено 22.10.2026)

- **CI, job `audit`:** `pip-audit` по `backend/requirements.txt` и `requirements-dev.txt`, `npm audit --audit-level=high` по `frontend/` и `e2e/` (только lock-файлы, ничего не ставится). На 22.10: уязвимостей нет.
- **Не блокирует деплой** намеренно: свежая уязвимость, опубликованная ночью, не должна мешать выкатить исправление демо. Красный job чинится следующим PR — обновлением версии.
- **`postman/` (newman) не проверяется:** последняя версия newman 6.2.1 тянет транзитивные пакеты с известными уязвимостями (faker, lodash, handlebars и др.), «исправление» npm — откат на newman 4. Риск принят: newman запускается только в CI, гоняет нашу же коллекцию против локального стека и в продукт не попадает.
- Все версии закреплены точно (`==` в requirements, `package-lock.json`, `npm ci`); новые зависимости — только через лида. Действия GitHub закреплены по SHA коммита, образы Docker — по точной версии.
