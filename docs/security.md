# Безопасность

Документ задачи L8. Здесь собрано, что проверено и как защищено; разделы добавляются по мере прохода чек-листа L8. Сквозные правила — [AGENTS.md](../AGENTS.md), раздел «Безопасность».

## Загрузка документов (проверено 21.10.2026)

Клиент загружает выписки, договоры и отчётность (`POST /api/applications/{id}/documents`), сотрудник банка их скачивает. Опасность двойная: файл может навредить серверу, если тот его исполнит или разберёт уязвимой библиотекой, и тому, кто его откроет, — PDF-просмотрщик сотрудника выполняет встроенный JavaScript, запускает вложения и автодействия.

### Сервер файл не исполняет
- В бэкенде нет библиотек, которые разбирают PDF или изображения (ни PDF-парсеров, ни Pillow, ни ImageMagick): файл сервером не открывается, не рендерится и не конвертируется.
- Файл хранится под случайным именем `documents/<uuid>.<расширение по типу>` (`apps/documents/storage.py`); имя клиента — только для показа, в путь не попадает (`names.py`).
- Права на файл — `0640`, на каталог — `0750` (`FILE_UPLOAD_PERMISSIONS`): без бита исполнения, другим пользователям системы не читается.
- Каталог `media` не отдаётся веб-сервером: в Caddy нет маршрута на него, файл можно получить только через API после проверки доступа.
- Отдача — всегда вложение (`Content-Disposition: attachment`), `X-Content-Type-Options: nosniff`, тип — тот, что определён по содержимому, не присланный клиентом; на всём сайте CSP `default-src 'self'` (`deploy/caddy/Caddyfile`). Браузер файл не исполняет и не показывает как HTML.

### Что проверяется при загрузке
По порядку, отказ — ответ 400 с понятным текстом, файл не сохраняется (`apps/documents/services.py`):
1. Доступ: заявка своей компании (чужая — 404), статус, в котором загрузка разрешена (иначе 409).
2. Размер: не пустой и не больше `UPLOAD_MAX_FILE_BYTES` (10 МБ; больше — 413).
3. Тип — по первым байтам, а не по имени и заголовку клиента: только PDF, PNG, JPEG (`signatures.py`).
4. Содержимое — `apps/documents/inspection.py`, только стандартная библиотека Python:
   - **во всех файлах** нет HTML, `<script>`, `<svg>`, `<iframe>`, `<?php`, `javascript:` — так ловятся «полиглоты»: картинка или PDF, которые браузер мог бы прочитать как страницу;
   - **PDF:** корректный заголовок `%PDF-1.0…2.0`; файл кончается на `%%EOF`, после него — только пробелы (иначе к PDF дописан другой файл); нет активного содержимого — `/JavaScript`, `/JS`, `/Launch`, `/EmbeddedFile(s)`, `/RichMedia`, `/XFA`, `/SubmitForm`, `/ImportData`, `/GoToE`, `/AA`; имена проверяются после раскрытия экранирования (`/J#61vaScript` = `/JavaScript`) и внутри сжатых потоков (FlateDecode распаковывается с лимитом 64 МБ на файл — защита от «zip-бомбы»); зашифрованный PDF отклоняется: его содержимое не проверить. `/OpenAction` сам по себе разрешён — им LibreOffice и сканеры открывают первую страницу; опасное, что он мог бы запустить, отклоняется по списку выше;
   - **PNG:** цепочка чанков с проверкой CRC, первый — `IHDR`, после `IEND` ничего нет;
   - **JPEG:** файл кончается маркером `FFD9` — ничего не дописано.
5. Отказ пишется в лог (`upload rejected: application, user, тип, причина`) — без содержимого файла.

Тесты: `apps/documents/tests/test_inspection.py` (JavaScript в действиях и в сжатом потоке, обфусцированные имена, Launch, вложения, XFA, автодействия, шифрование, HTML и программа после `%%EOF`, «zip-бомба», PHP и ZIP после картинки, битые PNG и JPEG), `test_security.py` (через API: вредоносный файл → 400, в базе и на диске ничего), `test_signatures.py`. Демо-PDF (`data/sample/documents`) и PDF коллекции Postman проверку проходят.

### Чего нет и почему
- **Антивирус (ClamAV и т. п.)** — отдельный сервис и зависимость; для синтетических демо-данных не нужен. На проде с реальными клиентами — обязателен, вместе с санитизацией PDF (пересборка без активного содержимого) перед показом сотруднику.
- **Проверка изображений декодером** — нужна библиотека (Pillow); структурной проверки и отказа от всего, что дописано после конца файла, для прототипа достаточно.
