# Фронтенд: карта сайта, маршруты, экраны, правила

Обязателен для всех задач C*, B* и для агентов, которые их делают. Дизайн — [design.md](design.md). Статусы и действия — [state-machine.md](state-machine.md). Контракт — [openapi.yaml](openapi.yaml), клиент — `frontend/src/api/` (генерируется). Если экрану не хватает поля или эндпоинта — стоп и вопрос лиду (AGENTS.md, правило 2).

## 1. Принципы
1. **Одна заявка — один экран статуса.** Клиент и банк смотрят на одну и ту же заявку: то, что сделал банк, клиент видит в таймлайне без перезагрузки (F5).
2. **Кнопки — только из `available_actions`.** Фронт не решает, что можно делать в каком статусе: показывает действия из ответа API. Недоступное действие не рисуется, а не «серое без объяснения».
3. **Ввод один раз (F12).** Реквизиты — из ЕГРЮЛ, подбор → предзаполненная заявка, черновик сохраняется сам. Повторный ввод того, что уже есть в данных, — баг.
4. **Понятно без банковских знаний (F11).** У каждого статуса — «что это значит» и «что дальше», у каждой причины — человеческий текст. Термины (DSCR, грейд) — только с пояснением.
5. **Состояние в URL.** Шаг мастера, вкладка карточки, фильтры очереди — в адресе: обновление страницы и ссылка «поделиться» не теряют контекст.
6. **Честность.** Данные симуляторов помечены «демо»; клиенту — «предварительная оценка», а не «решение банка», пока не подписан договор.

## 3. Охрана маршрутов (`src/app/guards/`)
| Охрана | Правило | Куда ведёт |
|---|---|---|
| `RequireAuth` | `getMe` → 401 | `/login?next=<текущий путь>` |
| `RequireKind("client")` / `RequireKind("bank")` | `me.kind` не тот | на свою главную: `/app` или `/bank` |
| `RequireCompany` | клиент и `me.company_id = null` (кроме `/app/company/new`) | `/app/company/new` |
| Публичные `/login`, `/register` | уже вошёл | `/app` или `/bank` по `me.kind` |
| `/bank/demo`, быстрый вход | `getDemoFailures` / `listDemoPersonas` → 404 | пункт меню не показываем |

Роль в компании (`signatory` / `preparer`) маршруты **не** закрывает: preparer видит заявку целиком, но без кнопок, которых нет в `available_actions`. Вместо «Отправить» у preparer — подсказка «Отправить может подписант: {имя из listCompanyMembers}».

## 4. Экраны: что обязательно
Для каждого экрана: загрузка (скелетон), пусто (текст + действие), ошибка (`error.message` из ответа + «Повторить»), 403/404 — отдельный экран. Готово, когда выполнен критерий задачи в [tasks.md](tasks.md) и шаг e2e зелёный.

### Вход и регистрация (C2)
- Перед первым небезопасным запросом — `GET /api/auth/csrf` (один раз при старте приложения).
- `/login`: логин, пароль; ошибка 401 — «Неверный логин или пароль», 429 — «Слишком много попыток, подождите минуту». Под формой на стенде — карточки демо-персон (код, название, сценарий) → `demoLogin` → своя главная.
- `/register`: логин, пароль (≥ 8), имя; без почты и телефона (O5). После — `/app/company/new`.
- Шапка: имя, компания и роль («Подписант» / «Готовит заявки»), колокольчик с `unread_count`, «Выйти» (`logout` → `/login`, очистить кэш запросов).

### Компания (C3)
- `/app/company/new`: поле ИНН (10 или 12 цифр) → `lookupCompany` → карточка из реестра (название, ОГРН, ОКВЭД с расшифровкой, адрес, директор, статус) → «Это моя компания» → `createCompany`. `registry_status ≠ active` — предупреждение «Компания в процессе ликвидации: кредит не выдадут» (сценарий 6, но создать можно). 503 — «Реестр временно недоступен, попробуйте через минуту».
- `/app/company`: реквизиты только для чтения с пометкой «из ЕГРЮЛ» (F12); можно поменять короткое название. Сотрудники: имя, должность, роль; приглашать, отзывать приглашения и убирать — только `my_role = signatory`. Приглашённый появляется в списке «Ждут ответа» и становится сотрудником, только когда сам примет приглашение на `/app/company/new` (D23). Подключения: «Счёт в банке» и «ЭДО» → `connectIntegration` → «Подключено (демо)», метрики появляются на главной.

### Подбор (C4) — центральный экран продукта
1. **Что случилось?** Четыре карточки простым языком, не названиями продуктов: «Не хватает денег до поступлений» (`cash_gap`), «Отгрузили, а покупатель платит позже» (`receivable_delay`), «Нужно закупиться к сезону» (`working_capital`), «Покупаю оборудование или транспорт» (`capex`).
2. **Параметры** — необязательные: сумма, срок; для `receivable_delay` — сумма отгрузки по УПД (`invoice_amount`).
3. **Предложения** (`createRecommendations`): по `rank`; у каждого — продукт, сумма, ставка, платёж (у возобновляемых — «платёж зависит от того, сколько возьмёте»), бейдж «подходит / есть ограничения», список причин (`ReasonList`). `stop_factors` — отдельный блок сверху «Почему сейчас не получится» + что сделать. Подпись: «Предварительная оценка по данным вашего счёта».
4. **«Оформить»** → `createApplication` (`prefill_source = recommendation`, продукт, сумма, срок, `need_type`, цель из шага 1) → `/app/applications/:id/edit/business`.
- Калькулятор (`calculateAnnuity`): сумма, ставка %, срок → платёж, переплата, график (сворачиваемый). Только вызов API, никакой арифметики на фронте.
- Каталог `/app/products`: карточки «для чего», «сколько и на какой срок», «что понадобится» (`required_documents`), кнопка «Подобрать под мою задачу».

### Мастер заявки (C5)
- Шаги в URL: `params` → `business` → `documents` → `review`; `Stepper` сверху; «Назад» не теряет данные.
- Заявка уже не `draft` (или нет `edit` в `available_actions`) → `replace` на `/app/applications/:id`.
- `/new` — только шаг `params`; «Далее» → `createApplication` → `replace` на `/:id/edit/business`. Дальше — черновик.
- **Автосохранение:** изменения полей → `updateApplication` с текущей `version` через 800 мс после последнего ввода; из ответа берём новую `version`. Индикатор «Сохранено · 12:04». 409 `version_conflict` → баннер «Заявку изменили в другой вкладке» + «Загрузить актуальную».
- `params`: тип потребности, цель, сумма, срок, продукт; `invoice_amount` — для факторинга; `collateral_description` — для `capex` («Что можете предложить в залог? Можно оставить пустым»).
- `business`: данные компании и последние метрики — **только чтение**, «Исправить в профиле» → `/app/company`.
- `documents`: чек-лист `required_documents` продукта: загружено ✓ / загрузить; PDF, JPG, PNG до 10 МБ; ошибки 400/413 — текстом у файла.
- `review`: сводка и «Отправить в банк» (если `submit` в `available_actions`). `Idempotency-Key` = `crypto.randomUUID()`, создаётся один раз на нажатие и переиспользуется при повторе после сетевой ошибки. После — `/app/applications/:id`.

### Заявка клиента (C6, C7)
Порядок блоков сверху вниз:
1. **Шапка:** продукт, сумма, `StatusBadge`, дата.
2. **«Что дальше»** (`NextStep`): текст по статусу из `texts/` + главная кнопка из `available_actions`.
3. **Оффер** (если `offer`): сумма (и запрошенная, если `is_counteroffer`), ставка, срок, платёж, «действует до»; при `is_counteroffer` — «Почему меньше, чем вы просили» + причины; при `product_changed` — «Почему другой продукт». Кнопки `accept_offer` → `/sign`, `decline_offer` — с подтверждением.
4. **Запросы банка** (`open_info_requests`): текст, какие поля или документы нужны, загрузка документов, поле ответа → `respondInfoRequest`.
5. **Решение** (`decision`): исход, причины (`ReasonList`), для отказа — «Что можно улучшить» (`improvements`); пометка «Предварительная оценка», если `is_preliminary`.
6. **Таймлайн** (`StatusTimeline` по `listApplicationEvents`).
7. **Документы.**
- **Обновление без перезагрузки:** пока статус `submitted`, `processing`, `signed` — опрос каждые 3 с; иначе — каждые 15 с; смена статуса — тост и `aria-live`.
- `/sign` (C7): `startSignature` → крупно код из 6 цифр, «действует N минут», «попыток: 3» → поле кода → `confirmSignature`. Ошибка — текст из ответа (там остаток попыток). Успех → заявка; статус `signed`, затем `issued` («Деньги отправлены на счёт»). Подпись — «код на экране вместо SMS: так по условиям прототипа».

### Главная и уведомления (C8)
- Главная: заявки, где нужно действие клиента (`info_requested`, `offer`, `signing`, `draft`), — первыми; ключевые метрики (`getCompanyMetrics`) как карточки «значение — порог — понятный текст»; если снимка нет — «Подключите счёт, чтобы мы посчитали» → `/app/company`.
- Колокольчик: опрос `listNotifications?unread=true&page_size=5` раз в 20 с; клик по уведомлению → заявка + `markNotificationRead`.

### Очередь банка (B3)
- Счётчики по статусам — кликабельные чипы (`counters`).
- Фильтры в URL: `status` (несколько), `product_kind`, `grade`, `assignee` (`me` / `none` / все), `min_hours_in_status`, `search` (ИНН или название); сортировка; 20 строк на страницу.
- Колонки: №, компания и ИНН, продукт, сумма, статус, грейд, исполнитель, «в статусе N ч», просрочка по нормативу (`is_overdue`, `overdue_hours` с сервера — своих порогов на фронте нет, XP4), значок «источник недоступен». Фильтр «Просрочено» — параметр `overdue`. Строка → карточка.
- Опрос раз в 15 с.

### Карточка банка (B4, B5)
- Шапка: компания, сумма, продукт, статус, грейд, исполнитель, `source_unavailable`.
- Вкладки (`?tab=`): **Заявка** (параметры, оффер, история решений), **Клиент** (реквизиты, сотрудники, метрики снимка), **Проверки** (четыре источника: статус значком и словами, `summary`, «что это значит» — к какому исходу ведёт статус; сведения источника подписанными полями, без ключей и кодов, признаки риска словом; происхождение — время ответа, версия симулятора, SHA-256; `unavailable` — «источник не ответил», SRC4, SRC6), **Скоринг** (`ScoreBreakdown`: факторы, баллы, итог, грейд, версия модели), **Документы** (скачивание), **Журнал** (все события, включая внутренние, + поле комментария).
- Панель действий — только из `available_actions`; каждое — в диалоге с подтверждением и обязательными полями:
  - `approve` — комментарий клиенту (необязательно);
  - `counteroffer` — сумма, срок, ставка %, продукт (тот же или другой), комментарий; подсказка — допустимая сумма из `reasons` решения;
  - `request_info` — текст и нужные типы документов;
  - `decline` — причины простым языком и минимум один пункт «что улучшить».
- Каждое действие отправляет `version` из загруженной карточки. 409 `version_conflict` → «Заявку уже изменили» + перезагрузка карточки, введённое в диалоге не теряем.

### Дашборд и демо-панель (B6, B7)
- Дашборд: период (7 / 30 / 90 дней), воронка по этапам, среднее время в статусах, доля авторешений; пусто — «Заявок за период нет».
- Демо-панель: переключатели сбоев четырёх источников (`setDemoFailures`) и у каждого — живой статус circuit breaker (`getDemoSources`, опрос раз в 2 с): «закрыт · вызовы идут», «открыт · 3 ошибки подряд · повтор через 24 с», «пробный вызов», плюс когда сбой погаснет сам; «Сбросить демо-данные» (подтверждение), список персон с «Войти». Сценарий 7 — в два клика: выключили БКИ → вошли за персону 7; после её заявки breaker БКИ открыт (XP6).

### Ассистент (B8)
- Панель справа (~420 px) на всех `/app/*`; на странице заявки передаёт `application_id`.
- Ответ — только текст (никакого HTML); под ответом — свёрнутое «Что сделал ассистент» (`tool_calls`).
- `pending_action` → карточка «Ассистент предлагает: {summary}» и кнопки «Подтвердить» / «Отмена»; без подтверждения ничего не отправляется.
- 429 — «Слишком много сообщений, подождите минуту».

## 5. Правила кода
### Структура
```
src/app/            router.tsx, routes.ts, layouts/, guards/, providers.tsx
src/features/<f>/   страницы и компоненты фичи, api.ts (хуки запросов), schema.ts (zod), *.test.tsx
src/components/     дизайн-система (B1): StatusBadge, ReasonList, MoneyText…
src/components/ui/  примитивы shadcn
src/lib/            format.ts, money.ts, errors.ts, idempotency.ts
src/texts/          все тексты статусов, причин, действий, ошибок (D8)
```
Папка фичи = зона задачи: `auth` (C2), `company` (C3), `match`, `products` (C4), `application-wizard` (C5), `applications` (C6), `offer`, `signing` (C7), `home`, `notifications` (C8), `styleguide` (B1), `bank-queue` (B3), `bank-application` (B4, B5), `bank-dashboard` (B6), `bank-demo` (B7), `assistant` (B8), `landing` (B9). Чужие папки не трогаем; общий компонент нужен — просим B1.

### Данные
- Только `api` из `src/api/client.ts` (openapi-fetch, CSRF уже в нём). Никаких `fetch` и ручных URL.
- TanStack Query; ключи: `["me"]`, `["company"]`, `["company", "members"]`, `["company", "metrics"]`, `["products"]`, `["applications"]`, `["application", id]`, `["application", id, "events"]`, `["application", id, "documents"]`, `["notifications", params]`, `["bank", "queue", params]`, `["bank", "application", id]`, `["bank", "dashboard", days]`.
- Мутация, вернувшая `ApplicationDetail` / `BankApplicationDetail`, кладёт ответ в кэш (`setQueryData`) и инвалидирует списки и таймлайн.
- Ошибки: `details` из ответа → ошибки полей формы (`setError`); `message` — текст для человека; 409 `version_conflict` и `invalid_transition` → перечитать заявку и показать сообщение.
- Формы: react-hook-form + zod; схемы рядом с фичей, ограничения — как в контракте (длины, диапазоны).

### Деньги, ставки, даты (`src/lib/format.ts`)
- Деньги приходят строкой `"900000.00"` и уходят строкой. Арифметики с деньгами на фронте нет — все расчёты на бэке (`calculateAnnuity`, `createRecommendations`).
- `formatMoney("2009314.00")` → `2 009 314 ₽` (копейки — только если не ноль); `formatRate("0.2400")` → `24 %`; ввод ставки в процентах → `"0.24"`.
- `MoneyInput` (B1): цифры с разрядами при вводе, на выходе строка `"900000.00"`.
- Даты — `Intl.DateTimeFormat("ru-RU")`, часовой пояс браузера; «через 3 дня», «12 мин назад» — для уведомлений и таймлайна.

### Тексты
- Все строки интерфейса — в `src/texts/` (D8), по ключам из типов контракта: `Record<Schemas["ApplicationStatus"], StatusText>` — TypeScript сам укажет, если статус забыли.
- Для статуса: `label`, `meaning` («что это значит»), `next` («что дальше»); для `reasons.metric` — название и пояснение; для действий — подписи кнопок и подтверждений.

### Тесты и e2e
- Vitest — для логики: `format`, `MoneyInput`, охраны, преобразование ошибок, `NextStep` по статусам.
- Playwright ищет элементы по ролям и подписям (`getByRole("button", { name: "Отправить в банк" })`), поэтому у всех кнопок и полей — видимые подписи или `aria-label`. `data-testid` — только когда иначе никак.
- Шаги e2e — [e2e/journey.spec.ts](../e2e/journey.spec.ts), владельцы — D18.

### Запрещено
`dangerouslySetInnerHTML`, токены в `localStorage`, свои запросы мимо `api`, арифметика с деньгами, кнопки действий заявки без `available_actions`, новые зависимости без лида.
