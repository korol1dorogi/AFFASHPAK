## Профиль нагрузки

Разгон 30 с до 50 VU → 2 мин держим 50 → спад 15 с. Каждый VU один раз входит через демо-вход (`/api/auth/csrf` → `/api/demo/login`) и дальше живёт в своей сессии, как отдельный браузер.

| Сценарий | Кто | Что делает VU |
|---|---|---|
| `match.js` | 9 клиентских персон, ~6 VU на персону | `POST /api/recommendations` с одним из 7 запросов формы `/app/match` (все 4 потребности, с суммой и сроком и без), пауза 1–3 с |
| `queue.js`, `PROFILE=realistic` | одна персона банка, 50 VU | как фронт: `GET /api/bank/applications` раз в 15 ± 2 с (`refetchInterval`) с одним из 14 наборов фильтров, сортировок и страниц, `page_size=20`; на каждом третьем проходе — карточка `GET /api/bank/applications/{id}` и 5–10 с на ней |
| `queue.js`, `PROFILE=stress` | одна персона банка, 50 VU | то же, но каждый проход очередь + карточка и пауза 1–3 с — где срабатывает троттлинг |

Пороги: `http_req_failed` < 1 %, p95 ответов 200 < 800 мс для подбора и < 500 мс для очереди и карточки. Латентность считаем только по ответам 200.

**Воркер Celery** поднят во всех прогонах и стоит отдельной строкой. Подбор и очередь в него не ходят: по логу воркера за время прогонов задач нет. После каждого сброса демо-данных он ~3 с выполняет `pipeline.disburse` и `pipeline.run` засеянной очереди, и это заканчивается до старта k6. Пики CPU у воркера — его healthcheck: `celery inspect ping` раз в 10 с запускает отдельный процесс Python. ОЗУ воркера (~290 МиБ) от нагрузки не зависит.

После каждого прогона `/api/ready` → 200 (`reset.js` с `SKIP_RESET=1`).

### runserver, DEBUG=1: stress, очередь с паузой 1–3 с

Одна демо-персона банка: лимит 600/мин на пользователя срабатывает при ~10 req/s (номинал) — это SEC1, защита, а не узкое место. 429 — ожидаемые ответы: отдельная метрика `throttled_429`, в `http_req_failed` не входят.

| Метрика | Значение |
|---|---|
| Всего запросов | 6 717, 40,1 RPS |
| Ответов 429 (`throttled_429`) | 3 398 (51 %), 20,3 в секунду |
| Ответов 200 | 3 219 (очередь и карточка), ~19 в секунду за весь прогон |
| Прочие ошибки | 0 |
| Очередь, только 200 | p50 103 мс, p95 442 мс, p99 622 мс, макс. 986 мс — порог < 500 мс держит |
| Карточка, только 200 | p50 112 мс, p95 400 мс, p99 560 мс, макс. 844 мс — порог < 500 мс держит |
| Пик ресурсов | backend 142 % CPU / 293 МиБ, db 35 % / 194 МиБ, web 7 %, worker 70 % (healthcheck) |

Как проверили, что режет именно `user`: в кэше троттлинга (`django_cache`) во время прогона копятся ключи `throttle_user_*`. Отдельный последовательный пробник после паузы получает первый 429 ровно на 601-м запросе за минуту, ответ `{"error": {"code": "throttled", …}}`, `Retry-After` в секундах. `demo_login` (50 входов за 30 с при лимите 120/мин) и `anon` не срабатывают. Лимиты не меняли.

Наблюдение для SEC1: при 50 параллельных запросах одного пользователя проходит ~19 ответов 200 в секунду, почти вдвое больше номинальных 10. DRF `SimpleRateThrottle` читает историю из кэша и записывает её обратно без блокировки, поэтому параллельные запросы одного пользователя теряют часть записей. На последовательных запросах лимит точный.

### gunicorn, 3 воркера, DEBUG=0 (как на стенде)

Отдельный контейнер из того же образа бэкенда (`docker compose run --no-deps`, порт `127.0.0.1:8099`, удалён после прогона). Код примонтирован, как в локальном compose. Команда — как в `docker-compose.prod.yml`: `gunicorn config.wsgi:application --workers 3 --timeout 60 --access-logfile -`. Окружение — как у стенда: `DJANGO_DEBUG=0`, `THROTTLE_LOGIN=10/min`, `THROTTLE_DEMO_LOGIN=120/min`, `THROTTLE_ANON=300/min`, `user` 600/мин.

Единственное отличие от стенда — HTTPS. TLS перед контейнером нет, поэтому модуль настроек вне репозитория импортирует `config.settings` и выключает только `SECURE_SSL_REDIRECT`, `SESSION_COOKIE_SECURE`, `CSRF_COOKIE_SECURE` и HSTS. Без этого Django редиректит на HTTPS, а k6 не отдаёт Secure-cookie по HTTP. Caddy в цепочке нет: на runserver он брал не больше 7 % CPU. База, Redis и воркер — те же, что у локального стека. Перед каждым прогоном — сброс демо-данных, после — `/api/ready` → 200.

## Где узкое место

- **В темпе фронта узкого места нет.** Подбор и очередь отвечают в пределах 52 мс по p95 при 50 пользователях. CPU бэкенда — не выше 74 %, то есть меньше одного ядра из шестнадцати; ОЗУ всего стека — ~0,85 ГБ, из них ~0,6 ГБ приходится на два процесса Django (backend и worker).
- **Первым упирается бэкенд, а не база.** В stress при 40 RPS бэкенд берёт 142 % CPU, база — 35 %, и p95 успешных ответов вырастает с 52 до 440 мс. Это `runserver`, один процесс Python, его ограничивает GIL. На gunicorn с 3 воркерами и `DEBUG=0` упора нет: в stress p95 успешных ответов — 45 мс вместо 442, CPU — 79 % на три процесса. Каждый запрос дополнительно читает и пишет счётчик троттлинга в `DatabaseCache` в Postgres — это цена общего лимита на все процессы (SEC1).
- **Самые тяжёлые ответы** — очередь (счётчики по статусам + страница) и карточка (заявка, компания, проверки, скоринг, журнал). Под stress они растут одинаково. Подбор под той же частотой запросов (21,8 RPS) остаётся на p95 52 мс.
- **Лимит одной персоны.** 50 сотрудников за одной учёткой — артефакт демо: в банке у каждого своя учётка и свой лимит 600/мин. В темпе фронта (раз в 15 с) лимит не достигается.

Мелочь сценария: в realistic спад 15 с короче итерации (до 27 с), поэтому k6 показывает 26 «interrupted» итераций. Это VU, оборванные во время паузы: запросы не теряются, в ошибки не идут.

## На стенде

Доступа к VPS у нас нет — заполнить после OPS1. k6 запускать с ноутбука, не на VPS: иначе k6 заберёт CPU у стенда. На стенде должен быть `DEMO_MODE=1`. Все VU придут с одного IP: `demo_login` 120/мин хватает на 50 входов за 30 с разгона, `/api/auth/csrf` идёт под `anon` (на стенде 300/мин).

```bash
for s in reset.js match.js queue.js; do
  docker run --rm --network host -v "$PWD/scripts/k6:/scripts:ro" -e BASE_URL=https://<домен стенда> grafana/k6:1.3.0 run /scripts/$s
done
docker run --rm --network host -v "$PWD/scripts/k6:/scripts:ro" -e BASE_URL=https://<домен стенда> -e SKIP_RESET=1 grafana/k6:1.3.0 run /scripts/reset.js
```

Ресурсы — на VPS во время прогона: `scripts/k6/stats.sh record stats.csv`, затем `scripts/k6/stats.sh peak stats.csv` (контейнеры проекта `alfa-cabinet`; если на стенде другое имя проекта — `COMPOSE_PROJECT_NAME`).
