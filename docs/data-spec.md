> v1 · `generator_version = "datagen-2026.10-v1"`. Закрывает T5, O3 ([case.md](case.md)). Исполнитель — генератор S2 (`backend/apps/demo_data/`), потребители — симуляторы S1 и `seed_demo`, калибровка — D9.
> Имена сущностей, полей и значений — только из [data-model.md](data-model.md) и моделей `backend/apps/*/models.py`. Формулы — только функции `backend/apps/credit_math/` ([knowledge/credit.md](knowledge/credit.md)); пометка «**для S2**» — функции нет, S2 пишет её по описанию (где ей жить — раздел 12). Продукты — [products.md](products.md) (D3), скоринг и правила — [decision-model.md](decision-model.md) (D4). Пометка «**допущение**» — значения нет в репозитории, выбрано здесь, причина — одной строкой.

## 1. Назначение и принципы

| Принцип | Что это значит для генератора |
|---|---|
| Один генератор — один источник правды | `generate(seed, generator_version, as_of, n_companies) → dict`, сериализуется в один JSON (раздел 2). Из него читают симуляторы S1 (ответы по ИНН) и `seed_demo` (строки БД). Других источников синтетики нет ([decisions.md](decisions.md), D9) |
| Детерминизм | Тот же `seed` + `generator_version` + `as_of` + `n_companies` → байт-в-байт тот же JSON (ключи отсортированы, `ensure_ascii=False`, отступ 2). Ни текущей даты, ни `uuid4`, ни `hash()` — только `random.Random` от строкового зерна (раздел 6.6) |
| Опорная дата | `as_of = 2026-10-01` (**допущение**: начало недели хакатона, все выписки — полные месяцы до неё). Все даты генератора считаются от `as_of`, а не от «сегодня» |
| Параметры по умолчанию | `seed = 2026`, `n_companies = 240` (засев). Для D9 тот же генератор запускается с `n_companies = 5000` — только расчёт, без засева (раздел 6.5) |
| Всё синтетика (O3) | Компании, люди, адреса, выписки, документы, заявки выдуманы. Реальных людей и компаний нет; данные кейса не используются (их нет, D9) |
| Метка «демо» | `is_demo = true` у каждой `Company` и `UserProfile`. Строка «(демо)» — в конце каждого `name`, `full_name`, `director_name`, `address`, `counterparty`, `purpose`, `summary`, `message`, `original_name`; в PDF-заглушках — водяной знак «ДЕМО» |
| Регион 00 | ИНН и ОГРН — с валидной контрольной суммой и кодом региона `00`: такого региона нет, совпадение с реальной организацией исключено (раздел 3) |
| Без секретов | Паролей, ключей и кодов подписи в JSON нет: пароли задаёт `seed_demo` из `.env`/фикстур, коды подписи — только хеш (раздел 8) |
| Снимок = функция выписки | Поля `FinancialSnapshot` из выписки никогда не задаются «руками»: генератор строит выписку под целевые значения и записывает в снимок то, что **пересчитано** из выписки (раздел 4). Отчётные поля (`revenue`, `ebitda`, …) задаются напрямую |

## 2. Формат выходного JSON

Ключи верхнего уровня и записей — имена полей моделей. Служебные поля генератора (в модели не пишутся) — с префиксом `_`.

| Тип | Формат | Пример |
|---|---|---|
| Деньги (`Decimal(14,2)`) | строка, точка, 2 знака | `"3000000.00"` |
| Коэффициент, ставка (`Decimal(8,4)`) | строка, доля, 4 знака | `"0.1000"`, `"0.2000"` (= 20%) |
| Дата | ISO `YYYY-MM-DD` | `"2023-10-01"` |
| Дата-время | ISO UTC с `Z` | `"2026-09-14T09:30:00Z"` |
| Период снимка | `YYYY-MM` | `"2026-09"` |
| Нет значения | `null` (не `0`, не `""`) | `"ebitda": null` |
| Ссылка на запись | служебный `_key` записи (строка) | `"company": "co_coffee_shop"` |

### 2.1. Разделы

| Раздел | Запись (поля) | Кто читает |
|---|---|---|
| `meta` | `generator_version`, `seed`, `as_of`, `n_companies`, `is_demo: true`, `counts` (число записей по разделам) | все |
| `companies[]` | `_key`, `legal_form`, `name`, `inn`, `ogrn`, `okved`, `okved_name`, `registered_at`, `region`, `address`, `registry_status`, `director_name`, `is_demo`, `created_at` (= `as_of`, 00:00Z); служебные: `_persona` (код или `null`), `_okved_group` (раздел 6.2) | seed, S1 (`egrul`) |
| `users[]` | `_key`, `username`, `profile: {kind, full_name, is_demo}`; служебное `_login_enabled` (bool, раздел 8) | seed |
| `memberships[]` | `user`, `company`, `role`, `position` | seed |
| `financial_snapshots[]` | `company`, `period`, `source = "simulator"`, `cleaned_credit_turnover`, `cfads`, `debt_service`, `revenue`, `cogs`, `ebitda`, `debt`, `cash`, `receivables`, `inventory`, `payables`, `counterparty_concentration`, `revenue_trend` | seed, S1 (`bank_account`) |
| `statements[]` | `company`, `account_masked`, `period_from`, `period_to`, `transactions[]` — `date`, `direction`, `amount`, `counterparty`, `counterparty_inn`, `category`, `purpose` (формат — [data/SCHEMA.md](../data/SCHEMA.md) + `counterparty_inn`, раздел 4.1) | S1 (`bank_account`) |
| `simulators` | `egrul`, `transparent_business`, `bki`: словари `inn → {status, data}` (раздел 5). `bank_account` отдельно не дублируется: симулятор берёт `statements[]` и `financial_snapshots[]` по ИНН компании | S1 |

| `personas` | `код → {company, application, users}` — ключи записей персон 1–7 (раздел 9) | seed, e2e, тесты D5 |
| `edge_cases[]` | `{code, company, snapshot, checks, application, expected}` — Г1–Г10 и прочие края (раздел 10); `seed_demo` их не засевает | тесты D5, L4 |
| `_latent` | `company → {segment, pd, default_12m}` (раздел 6.4); `seed_demo` раздел не читает | D9 |

Каталог продуктов в JSON не дублируется: его грузит фикстура D3 (`loaddata products`), заявки ссылаются на `Product.code`.

## 3. Идентификаторы, имена, адреса

### 3.1. ИНН и ОГРН (код региона 00)
`d1…dn` — цифры слева направо; `Σ` — сумма произведений цифр на веса.

| Идентификатор | Кому | Структура | Контрольные цифры |
|---|---|---|---|
| ИНН, 10 цифр | ООО | `00` (регион) + `01` (инспекция) + 5 цифр номера + 1 контрольная | `d10 = (Σ d1…d9 × [2, 4, 10, 3, 5, 9, 4, 6, 8]) mod 11 mod 10` |
| ИНН, 12 цифр | ИП (и физлица — учредители, раздел 8) | `00` + `01` + 6 цифр номера + 2 контрольные | `d11 = (Σ d1…d10 × [7, 2, 4, 10, 3, 5, 9, 4, 6, 8]) mod 11 mod 10`; `d12 = (Σ d1…d11 × [3, 7, 2, 4, 10, 3, 5, 9, 4, 6, 8]) mod 11 mod 10` |
| ОГРН, 13 цифр | ООО | `1` + `ГГ` (две последние цифры года `registered_at`) + `00` (регион) + `01` (инспекция) + 5 цифр номера + 1 контрольная | `d13 = (число из d1…d12) mod 11 mod 10` |
| ОГРНИП, 15 цифр | ИП | `3` + `ГГ` + `00` + `01` + 7 цифр номера + 1 контрольная | `d15 = (число из d1…d14) mod 13 mod 10` |

- **Номера компаний.** Один номер на компанию: ИНН и ОГРН берут номер из одного счётчика её правовой формы (отдельно ИП и ООО). `1–99` зарезервированы за персонами и не зависят от `seed` (персона N — номер N), края — с `100` в порядке раздела 10, отдельно по ИП и ООО, популяция — с `1000` подряд в порядке генерации. Так ИНН уникальны по построению, а ИНН персон одинаковы при любом зерне.
- **Контрагенты в выписках** с `counterparty_inn` — ООО с инспекцией `02` (`0002…`): один счётчик с 1 в порядке персоны → края → популяция; одно имя = одна организация = один ИНН (повторное имя получает тот же ИНН). В `companies[]` их нет, это только плательщики, получатели и кредиторы.
- **Учредители** — физлица, ИНН 12 цифр с инспекцией `03`: одно ФИО = один человек = один ИНН. Исключение: учредитель ИП — сам ИП, его `inn` = ИНН ИП.
- **Проверка** (раздел 11): у каждого ИНН и ОГРН контрольные цифры совпадают с пересчитанными, длина — 10/13 у ООО и 12/15 у ИП, `inn[0:2] == "00"`, у ОГРН `ogrn[3:5] == "00"` и `ogrn[1:3]` = год `registered_at`.
- Реквизиты персон — в разделе 9.1.

### 3.2. Маска счёта
`account_masked` (в `statements[]` и `Disbursement`): 20 символов = балансовый счёт (`40802` у ИП, `40702` у ООО) + `810` (рубли) + `••••••••` (8 точек) + последние 4 цифры ИНН. Пример: `40802810••••••••0170`. Полного номера счёта в JSON нет; контрольный разряд не считается (**допущение**: номер не показывается целиком и ни с чем не сверяется).

### 3.3. Имена, названия, адреса
- **Люди.** ФИО собираются из фиксированных списков в коде генератора: 40 фамилий, 30 мужских и 30 женских имён, 30 отчеств (частотные, но в сочетании вымышленные), с согласованием по роду; к `full_name` и `director_name` добавляется « (демо)». Совпадение сочетания с реальным человеком не исключено, поэтому метка «(демо)» обязательна, а других персональных данных (дат рождения, паспортов, телефонов, email) генератор не создаёт.
- **ООО:** `ООО «{прилагательное} {существительное}» (демо)` из списков по группе ОКВЭД (раздел 6.2), например «ООО «Северная мебель» (демо)». **ИП:** `ИП {Фамилия} {Имя} {Отчество} — {вид бизнеса} «{вывеска}» (демо)`. Слова, повторяющие известные бренды, в списки не включаются.
- **`region`** = `"Демо-регион (00)"` у всех (**допущение**: формат поля в data-model не задан; так видно, что регион вымышленный).
- **`address`** = `{индекс 0000NN}, Демо-регион, г. {Условный | Примерный | Тестовск | Образцовск}, ул. {из списка 30 улиц}, д. {1–120} (демо)`. У компаний с флагом `mass_address` (раздел 5) — один из 3 «массовых» адресов, общий для нескольких компаний.
- **`okved_name`** — официальное наименование кода ОКВЭД 2 (раздел 6.2): это публичный классификатор, не персональные данные.

## 4. Выписки по счёту и `FinancialSnapshot`

### 4.1. Формат и категории
Транзакция — колонки [data/SCHEMA.md](../data/SCHEMA.md) (`date`, `direction`, `amount`, `counterparty`, `category`, `purpose`) плюс `counterparty_inn`: ИНН плательщика или получателя, `null` у розницы (эквайринг, наличные, физлица), у «Сотрудников», ФНС и своих счетов. В SCHEMA.md этой колонки нет — **предложение лиду** (раздел 12). `amount` — всегда положительный, направление задаёт `direction`.

| `category` | `direction` | Что это | В очищенный оборот | В `cfads` | В `debt_service` |
|---|---|---|---|---|---|
| `revenue` | `credit` | выручка: эквайринг, оплата покупателей | да | да, «+» | нет |
| `own_transfer` | `credit` / `debit` | переводы между своими счетами | нет | нет | нет |
| `loan` | `credit` | выдача кредита или займа | нет | нет | нет |
| `refund` | `credit` | возврат ошибочного списания, возврат от поставщика | нет | нет | нет |
| `payroll`, `rent`, `supplier`, `tax` | `debit` | операционные списания | — | да, «−» | нет |
| `loan_payment` | `debit` | платёж по кредиту или лизингу (тело и проценты) | — | нет | да |

Других комбинаций генератор не создаёт (например, `refund` с `debit`).

### 4.2. Период и окна
- Выписка — 18 полных месяцев до `as_of`: месяцы `t = 1…18` = 2025-04 … 2026-09, `period_from = 2025-04-01`, `period_to = 2026-09-30`; `FinancialSnapshot.period = "2026-09"`.
- Если бизнес моложе: выписка начинается с месяца, следующего за месяцем `registered_at`; `h` — число полных месяцев выписки (≤ 18).
- **Окно** `W` — последние `min(12, h)` месяцев (при `h = 18` это `t = 7…18`, 2025-10 … 2026-09). По окну считаются `cleaned_credit_turnover`, `cfads`, `debt_service`, `counterparty_concentration`.
- **Тренд**: при `h ≥ 15` — `t = 16…18` к `t = 4…6` (те же месяцы год назад, `year_over_year=True`); при `6 ≤ h < 15` — последние 3 месяца к предыдущим 3 (`year_over_year=False`, у метрики пометка `credit_math` «сезонность не учтена»); при `h < 6` — `revenue_trend = null` (корзина тренда не разыгрывается, раздел 6.3). При `h = 6` окно и тренд занимают одни и те же 6 месяцев, поэтому сумма окна задана построением: `cleaned_credit_turnover` = фактическая сумма окна / 6, а `cfads`, `κ`, `τ` — точные.

### 4.3. Как выписка превращается в снимок
Определения — [credit.md](knowledge/credit.md); функции — `credit_math`. Помесячная агрегация выписки в `credit_math` отсутствует — это функция **для S2** `statement_metrics(transactions, as_of)`; где ей жить — раздел 12. `inflow(t)` — сумма `revenue`-поступлений месяца `t`, `opex(t)` — сумма `payroll + rent + supplier + tax` месяца `t`, `|W|` — число месяцев окна.

| Поле `FinancialSnapshot` | Как считается | Функция |
|---|---|---|
| `cleaned_credit_turnover` | `round_money(Σ_W inflow(t) / |W|)` — среднемесячные поступления без своих переводов, кредитов и возвратов (credit.md, `overdraft_limit`) | для S2; округление — `credit_math.round_money` |
| `cfads` | `round_money(Σ_W (inflow(t) − opex(t)) / |W|)` — очищенные поступления минус операционные списания, без погашения кредитов и своих переводов (credit.md, `dscr`) | для S2 |
| `debt_service` | `round_money(Σ_W loan_payment(t) / |W|)` — все платежи по долгам в месяц; нет платежей → `"0.00"` (не `null`: долга нет) | для S2 |
| `counterparty_concentration` | `counterparty_concentration(top_inflow, total_inflow)`: `total_inflow = Σ_W inflow(t)`; `top_inflow` — наибольшая сумма `revenue`-поступлений за окно от одного `counterparty_inn`; поступления с `counterparty_inn = null` входят в `total_inflow`, но плательщиком не считаются (розница — это много покупателей, а не один); нет ни одного плательщика с ИНН → `top_inflow = 0` | `credit_math.counterparty_concentration` |
| `revenue_trend` | `revenue_trend(round_money(Σ текущих 3 мес / 3), round_money(Σ базовых 3 мес / 3), year_over_year=…)` по окнам 4.2 | `credit_math.revenue_trend` |
| `revenue`, `cogs`, `ebitda`, `debt`, `cash`, `receivables`, `inventory`, `payables` | не из выписки: из «отчётности» компании (раздел 6.3), у ИП и ООО без отчётности — `null` | — |

Потребители считают остальное сами функциями `credit_math`: `dscr(cfads, debt_service)`, `debt_to_ebitda(debt, ebitda, cash)`, `overdraft_limit(cleaned_credit_turnover, alpha)`, `working_capital_need(...)`, `max_loan_by_dscr(...)`. В снимок они не пишутся.

### 4.4. Построение выписки под целевые числа
Вход: целевые значения компании — сумма окна `S_W` (= `|W|` × среднемесячный оборот, `|W|` — число месяцев окна, 4.2), `cfads`, `debt_service`, тренд `τ` (2 знака), концентрация `κ` (2 знака), группа ОКВЭД. У персон они из раздела 9, у популяции — из раздела 6.3. Все месячные итоги — в целых рублях; `r1000(x)`, `r10000(x)`, `r50000(x)` — округление до 1 000, 10 000 и 50 000 ₽ ROUND_HALF_UP: `Decimal(x) / шаг`, `quantize(Decimal(1), ROUND_HALF_UP)`, `× шаг` (`r10000` и `r50000` — для сумм заявок, раздел 7.5). `ΣM_W` — фактическая сумма `M(t)` по окну после шагов 2–4 (при `h ≥ 7` она равна `S_W`, при `h = 6` — задана шагами 2–3).

Округления шага (`r1000` / `r10000` / `r50000`), метод наибольшего остатка и раскладка сумм — в генераторе (`demo_data/amounts.py`); в `credit_math` — только `statement_metrics` (это построение данных, не кредитная формула).

| Шаг | Что делает генератор | Что гарантирует |
|---|---|---|
| 1. Форма | `raw(t) = S_W/|W| × s(месяц t) / s̄ × τ^((t − 12.5)/12)`: `s` — сезонность группы (4.5), `s̄` — её среднее; множитель `τ^…` даёт плавный рост или спад | правдоподобная помесячная динамика |
| 2. База тренда | `M(t) = r1000(raw(t))` для `t = 1…6`; `B = M(4) + M(5) + M(6)` | — |
| 3. Текущие 3 мес | `C3 = τ × B`; `M(16), M(17) = r1000(C3 × raw(t) / Σ raw(16…18))`, `M(18) = C3 − M(16) − M(17)` | `revenue_trend = τ` точно |
| 4. Остаток окна | `R = S_W − C3`; `M(t) = r1000(R × raw(t) / Σ raw(7…15))` для `t = 7…14`, `M(15) = R − Σ M(7…14)` | `Σ_W M = S_W`, оборот точно |
| 5. Операционные списания | `O(t) = r1000(M(t) × (1 − |W|·cfads / ΣM_W))` для всех `t`, кроме последнего месяца окна; последний месяц окна = `(ΣM_W − |W|·cfads) − Σ O` остальных месяцев окна | `cfads` точно |
| 6. Крупнейший плательщик | `K(t) = r1000(κ × M(t))`; последний месяц окна = `κ × ΣM_W − Σ K` остальных месяцев окна; у него свой `counterparty_inn` | `counterparty_concentration = κ` точно |
| 7. Остальная выручка | `M(t) − K(t)` делится между розницей (`counterparty_inn = null`, доля по группе, 4.5) и `n` другими плательщиками: `n = max(U{1…6}, n_min)`; без розницы `n_min = ⌈1/κ⌉ + 1`, с розницей `n_min = ⌈(1 − κ − доля_розницы)/κ⌉ + 1`; доли плательщиков почти равные (веса 95–105); без розницы последний плательщик поглощает помесячное округление. Правило — только для популяции; у персон плательщики заданы явно (9.2) | доля каждого другого плательщика с ИНН за окно строго меньше `κ`, крупнейший — именно `K` |
| 8. Долги | `debt_service` делится на `U{1…3}` обязательства: платежи 0.5 / 0.3 / остаток; вид — лизинг 25 %, кредит 75 %. Открыто внутри выписки 30 % — только кредиты и только если до окна есть месяц: месяц открытия `0…min(3, начало окна) − 1`, проводка `loan` на 12–24 платежа, платежи — со следующего месяца. Остальные открыты до выписки, дата равномерно в `[max(registered_at, period_from − 36 мес); period_from − 1 день]`. День платежа 10–20, каждое платится **все** месяцы окна; кредиторы «Банк (демо)» и «Лизинговая компания (демо)» — с ИНН (инспекция `02`) | `debt_service` точно |
| 9. Разбивка на проводки | `O(t)` делится на `payroll` (5-го числа, одна проводка «Заработная плата за {прошлый месяц}»), `rent` (1–3-го), `tax` (25-го), остаток — `supplier` (2–6 проводок в случайные дни); доли — по группе (4.5). Розница — ежедневные зачисления эквайринга «за предыдущий день» с весами дней недели (пт–сб × 1.2, вс × 0.9) и шумом ±10 %; плательщики с ИНН — 1–4 оплаты в месяц. Суммы в копейках, последняя проводка каждой группы месяца добирает остаток | итоги месяцев = `M`, `O`, `K` до копейки; все суммы > 0 |
| 10. Шум, не влияющий на метрики | `own_transfer`: 0–2 поступления и 0–2 списания в месяц по 5–15 % `M(t)`; `refund`: 0–1 в месяц на 0,1–1 % `M(t)` | метрики не меняются (категории исключены, 4.1) |
| 11. Контроль | пересчитать снимок функцией 4.3 и сравнить с целями | расхождение → ошибка генератора, а не «подгонка» |

- Положительность: если на шаге 4 или 5 какой-то месяц получился ≤ 0 (резкий спад и сильная сезонность), генератор уменьшает амплитуду сезонности вдвое и повторяет шаги 1–5 (не больше 3 раз), затем падает с ошибкой.
- Короткая история (`h < 18`): шаги те же на доступных месяцах, с `|W|` вместо 12. При `h < 15` база тренда — 3 месяца перед текущими 3; при `h < 6` шаги 2–3 пропускаются (тренда нет); при `h = 6` шаг 4 пропускается — окно целиком составлено шагами 2–3, оборот = `ΣM_W / 6`; окно — 4.2.
- Персоны строятся тем же алгоритмом, их помесячные итоги заданы явно (раздел 9.2), чтобы S2 сверял их с таблицей.

Корзины БКИ и ФНС выбираются риск-сегментом компании (раздел 6.3); внутри корзины значения такие:

- **Живой сбой** (персона 7, демо-панель): симулятор отвечает `unavailable` на любой ИНН, пока у источника `DemoState.failing = true`. Данные в JSON при этом не меняются, `seed_demo` ставит `failing = false` всем источникам.

### 6.4. Скрытый «истинный» риск (латентный PD) для D9
- `pd = min(0.9, base_pd(сегмент) × exp(0.4 × z))`, `z ~ N(0, 1)` из потока `latent|{i}`; `base_pd` — строка таблицы 6.3. У стоп-компаний `base_pd = 0.30` (**допущение**; в Gini они не участвуют: балла нет).
- `default_12m = (u < pd)`, `u ~ U(0, 1)` из того же потока.
- Пишется только в `_latent`: модель решения его не видит, в БД он не попадает.
- **Gini для D9:** у балла `Score.total` (меньше балл — выше риск) против латентного риска. Основная оценка — по ожиданию: по всем парам компаний `(a, b)` с весом `pd_a × (1 − pd_b)` доля пар, где `total_a < total_b` (ничья — 0.5), это AUC; Gini = 2 · AUC − 1. Дополнительно — по реализованному `default_12m` (шумнее). Симуляция: 0.47–0.52 (среднее 0.505) на 30 зёрнах × 240 компаний — порог D9 ≥ 0.4 выполняется. Это различающая способность **на синтетике**, а не на реальных дефолтах.

### 6.5. Расчёт долей: метод и результат
Баллы зависят только от корзин, поэтому расчёт ведётся на уровне корзин; значения внутри корзины на грейд не влияют.

1. **Матрица переходов.** Для каждого сегмента — 40 000 модельных компаний: корзины по правилу 6.3; ООО с вероятностью P(ООО), отчётность у ООО — с вероятностью 0.7; без отчётности `debt_to_ebitda` даёт 7 баллов (нейтральные, D4); «долга нет» (40 % корзины 0 `dscr`) при отчётности даёт 15; сумма баллов → грейд по порогам D4 (90 / 75 / 60 / 50).
2. **Доли сегментов** — целые проценты `w` (сумма 100), минимизирующие `Σ_g (Σ_s w_s·M[s][g] − цель_g / 95)²` полным перебором с шагом 1 %. Цель среди проскоренных — (15, 30, 25, 15, 10) / 95.
3. **Популяция** — квоты 6.1, признаки по 6.3, стоп-квоты отдельно.

| Сегмент | Средний балл | → A | → B | → C | → D | → E |
|---|---|---|---|---|---|---|
| R1 | 91.0 | 61.4 % | 37.2 % | 1.4 % | 0 | 0 |
| R2 | 78.7 | 5.4 % | 65.2 % | 28.3 % | 1.2 % | 0 |
| R3 | 64.8 | 0.1 % | 9.6 % | 67.2 % | 21.7 % | 1.4 % |
| R4 | 55.7 | 0 | 0.8 % | 24.4 % | 57.5 % | 17.3 % |
| R5 | 38.6 | 0 | 0 | 0.4 % | 8.0 % | 91.6 % |

Почему доли сегментов не равны долям грейдов: полоса D узкая (10 баллов) при разбросе суммы ±8–10, поэтому R4 наполовину перетекает в C и E, а R2 — в C. Квоты 23 / 32 / 19 / 18 / 8 это перетекание компенсируют.

| | A | B | C | D | E | стоп |
|---|---|---|---|---|---|---|
| Цель, % всех компаний | 15 | 30 | 25 | 15 | 10 | 5 |
| Ожидание (матрица × квоты × 0.95) | 15.1 | 29.8 | 25.2 | 14.7 | 10.2 | 5.0 |
| n = 5000, зёрна 1 / 2 / 3 | 14.2 / 14.9 / 15.1 | 31.3 / 29.0 / 30.0 | 24.3 / 26.2 / 24.4 | 15.0 / 15.1 / 15.4 | 10.2 / 9.8 / 10.0 | 5.0 |

| n = 240, мин … макс на 30 зёрнах | 10.4 … 18.3 | 25.4 … 37.9 | 20.0 … 30.4 | 12.1 … 17.9 | 8.8 … 12.1 | 5.0 |

- На 240 компаниях коридор ±5 п. п. выдерживается примерно на 95 % зёрен (10 из 200 выходят по одному грейду), а разброс между зёрнами — до 7 п. п. Причина — размер выборки, а не модель. Поэтому **стабильность ≤ 3 п. п. и коридор как жёсткий критерий проверяются на `n_companies = 5000`** (D4, раздел 9), засев — 240.
- **Отчётность при `h < 12` = `null`** (6.2) на доли не влияет заметно. `h < 12` бывает только в корзине возраста [6; 12), а она выпадает лишь у R5 (соседняя к основной 12–23 мес, вероятность 0.125); у таких ООО `debt_to_ebitda` становится нейтральным (7 баллов). Повтор метода 6.5 (200 000 компаний на сегмент): в строке R5 доля D — 7.73 → 7.78 %, E — 91.98 → 91.93 %; итоговые доли A–E меняются меньше чем на 0.01 п. п. Квоты не пересчитывались.

- Подстройка D9 — параметрами D4 (пороги, шкалы). Если меняется популяция (`p_main`, квоты), это новая `generator_version`, а таблицы этого раздела пересчитываются тем же методом.

### 6.6. Случайность и детерминизм
- Поток — `random.Random(f"{seed}|{generator_version}|{scope}|{key}")`: строковое зерно в CPython детерминировано между запусками. У персон и краёв на месте `seed` стоит строка `fixed` — их данные не зависят от зерна. Свой поток у каждой задачи: `segments`; `company|{i}` — признаки; `statement|{i}` — выписка; `latent|{i}`; `application|{i}`; `people|{i}`; `edge|{code}`. Изменение одной части не сдвигает остальные.
- Деньги не проходят через float: целые рубли — `randint`, двузначные коэффициенты — `Decimal(randint(lo·100, hi·100)) / 100`. Логнормальный `T` и `z` для PD считаются во float и сразу округляются до целых рублей / 4 знаков через `Decimal(str(…))`. На одной версии Python результат одинаков; версия Python зафиксирована в образе (T3).
- Порядок записей в JSON: персоны, краевые случаи, затем популяция по `i`; внутри компании — по дате.
- Для D9 есть режим `statements=False` (n = 5000): выписки не строятся, снимок берётся из целей. Это допустимо, потому что построение точное (4.4), а проверка 11.3 на засеве это подтверждает.

## 7. Заявки
У каждой компании популяции одна **основная** заявка. У 20 % решённых (раздел 7.2) есть ещё одна **историческая** — более ранняя, в финальном статусе. Статусы, переходы и роли — [state-machine.md](state-machine.md); номера переходов ниже — оттуда.

### 7.1. Два этапа: без D5/L4 и после
Score и Decision генератор **не придумывает**: он вызывает балльную карту `apps.scoring` (D5) и функцию решения конвейера L4 — ту же, что вызывает worker. Своих правил скоринга и решения у генератора нет. Поэтому засев идёт в два этапа:

| | Этап 1: D5 и L4 ещё нет | Этап 2: D5 и L4 в main |
|---|---|---|
| Что считается | только данные: компании, выписки, снимки, симуляторы, черновики | плюс validation → Check → Score → Decision → Offer и дальнейший путь по 7.3 |
| Заявок популяции | 240 (по одной на компанию) | 240 основных + 48 исторических = 288 |
| Статусы популяции (n = 240) | `draft` 144 (60 %) · `submitted` 60 (25 %) · `cancelled` 36 (15 %, из черновика, переход 15) | таблица 7.2 |
| Персоны | 2–6 — `draft` с документами (раздел 9.3); 1 и 7 не засеваются (`_seed: false`) | так же |
| Итого в БД | 245 | ≈ 293 |
| Что видно банку | очередь из `submitted` без проверок и скоринга | все статусы, проверки, разложение скоринга |

На этапе 1 `seed_demo` не ставит `submitted` в очередь Celery. После мержа D5 и L4 засев пересоздаётся на этапе 2 (сброс демо-данных). Очередь банка B3 со статусами `manual_review`, `info_requested`, `offer` и вкладкой «Скоринг» до этапа 2 показать нельзя — **D5 блокирует и B3** (раздел 12).

### 7.3. Журнал: события по переходам
Каждый переход пишет **ровно одно** `ApplicationEvent` с `from_status` и `to_status`; `kind` и `actor_kind` — по таблице переходов state-machine.md:

| Переход | `kind` | `actor_kind` / `actor` |
|---|---|---|
| 1 `submit` | `status_changed` | `client` / signatory компании |
| 2 `pipeline.start` | `status_changed` | `system` / null |
| 3 `stop_factor`, 4 `auto_*`, 6 `auto_decline` | `decision` | `system` |
| 4a `incomplete` | `info_requested` | `system` |
| 5 `needs_review` | `status_changed` | `system` |
| 7 `approve`/`counteroffer`, 9 `decline` | `decision` | `bank` / `assignee` |
| 8 `request_info` | `info_requested` | `bank` / `assignee` |
| 10, 10a `respond` | `info_responded` | `client` / signatory или preparer |
| 11 `accept_offer`, 12 `decline_offer`, 15 `cancel` | `status_changed` | `client` / signatory |
| 13 `confirm_signature` | `signed` | `client` / signatory |
| 14 `disbursement.done` | `issued` | `system` |

События без смены статуса (`from_status = to_status = null`): `document_uploaded` (каждый документ, `actor` — кто загрузил), `check_completed` (по одному на `Check`, `system`), `score_calculated` (`system`), `assigned` (`bank`, когда у заявки появляется `assignee`), `comment` (у 30 % заявок, которые смотрел сотрудник: «Проверил выписку, обороты стабильные (демо)»).

- `is_internal = true` у `check_completed`, `score_calculated`, `assigned` и `comment`, у остальных `false` (**допущение**: клиент видит смену статуса и решения, а внутреннюю кухню банка — нет).
- `message` — короткий текст события с «(демо)»; `payload` — для `decision`: `{outcome, grade}`, для `check_completed`: `{source, status}`, для `info_requested`: `{fields, document_kinds}`.
- `version` = число переходов + число событий `assigned` (**допущение**: так L2 увеличивает `version` на каждое изменение заявки).
- Повтор журнала проверяем так: проиграть события по таблице переходов от `draft` — должен получиться текущий `status` (раздел 11).

### 7.4. Время
- `ref_date` — дата отсчёта возраста бизнеса: `submitted_at` заявки (у черновиков — `as_of`). Возраст из 6.3 считается именно к ней, поэтому балл возраста в Score и при пересчёте совпадает.
- Основная заявка: `created_at = as_of − (1…120) дн.`, историческая — `as_of − (150…400) дн.`; время — рабочие часы 09:00–19:00 МСК, в JSON — UTC.
- Интервалы: `created → submitted` 10 мин – 3 дн. · `submitted → processing` 5 с · проверки 1–5 с · Score и авторешение — в пределах 30 с от `processing` · `assigned` 2 ч – 2 дн. · действие сотрудника 1 ч – 3 дн. · ответ клиента 1 ч – 2 дн. · `accept_offer` 1 ч – 5 дн. · подпись 2–10 мин · выдача 1–30 мин. Если цепочка выходит за `as_of`, все интервалы заявки пропорционально сжимаются.
- `status_changed_at` — время последнего перехода; `decided_at` — время последнего `Decision`; у черновика — `created_at` и `null`.
- `Offer.expires_at = Decision.created_at + 30 дн.` (**допущение**). Так как засев идёт позже `as_of`, `seed_demo` сдвигает **все** даты-время заявок, событий, офферов, подписей и выдач на целое число дней `сегодня − as_of`. Даты выписок, снимков и `registered_at` не сдвигаются (**предложение лиду**, раздел 12).

## 12. Допущения (O6) и предложения лиду

### 12.1. Допущения
- **Опорная дата и окна.** `as_of = 2026-10-01`; метрики считаются по последним 12 месяцам, тренд — год к году по последним 3 месяцам (credit.md). Снимок у компании один, на `as_of`; исторические заявки используют его же.
- **Распределения популяции** (правовая форма, отрасли, размер, доли статусов, `need_type`) выбраны экспертно, а не по статистике: данных кейса нет (D9). Доли грейдов при этом попадают в цель plan.md — раздел 6.5.
- **Риск-сегменты и латентный PD** — модель генератора, а не банка. Gini на синтетике показывает, что балльная карта различает сегменты, которые мы сами задали; о реальных дефолтах он ничего не говорит.
- **Значения, которых нет в D4**, — `cleaned_credit_turnover` персон 2–6, весь снимок персоны 6, плательщики и долги персон: подобраны под масштаб бизнеса и на баллы и исходы D4 не влияют.
- **Концентрация** считается только по плательщикам с ИНН: розница (эквайринг, наличные, физлица) — это много покупателей, а не один.
- **Выручка из отчётности** = сумма очищенных поступлений за окно; `cfads × 12 ≤ ebitda` у всех компаний с отчётностью.
- **Счёт, документы, подпись** — маска без контрольного разряда, PDF-заглушки с «ДЕМО», код подписи не хранится.
